# Decisions

The dated ledger of what the SC signed off, with the reason. Append-only: entries are added, never rewritten — this file is the provenance record (*when*, and by whose word), where the PHILOSOPHY layer carries the reasoning in prose. When a decision lands, it gets its entry here and the affected PHILOSOPHY.md is updated in the same change.

Only what the SC explicitly signed off in conversation belongs here. Written elsewhere is not sign-off.

## 2026-07-05

### blueprint.md is a mission artefact — referenced, never reproduced

A blueprint is the SC's pinned spec or walkthrough (a model diagram, an element table, an exact function), produced with the handler in the intent conversation — never by an operator phase; what an Engineer produces is class design, part of the means. It lands as `blueprint.md` in the mission directory and the mission *references* the file. Reason: a spec was dropped from a `mission.md` in transcription — a copy can be dropped, a reference cannot; the file is the vehicle.

### The interlocutor re-engages mid-mission

Execution can surface a question the intent never settled; the interlocutor returns, it is settled with the SC into `intent.md`, and execution resumes. Small calls ride the executor's report to the SC directly; what re-engages the interlocutor is a question about what the mission is *for*. Reason: not everything can be drawn out up front — some boundaries only show against concrete work (AppLayout's plan was blocked four times on exactly this).

### Equip and prepare, in the scribe — decided means said or agreed

Precision has an axis: exact about the *what* (goal, objectives, blueprint), silent about the *how* (the operator's means). Decided means the SC said it or agreed to it — correct, verified, or obvious does not qualify; even a true thing the SC never agreed to is not what he wanted. Thinking, questioning, and proposing are welcome upstream; recommendations are not, because they take the thinking that makes the decision the SC's own.

### handover defined; testament and handover go together

The testament carries the learning into the knowledge base; the handover exists only for session continuity — not a summary, but enough for the successor to reorient: where things stand, what is in flight, what to search the memory tool for.

### Changing the glossary requires a repo-wide word search first

An existing use with a different meaning either gets rewritten to the glossary's meaning, or the word was the wrong one to pick. Reason: `blueprint` was defined while the Engineer role already used the word for class design, and the term was muddied from birth.

### The editorial layer: PHILOSOPHY at scope, plus this ledger

Understanding-nature content lives in the PHILOSOPHY layer at the scope it governs (unit / `skills/` / root); decisions-nature content lives here, dated and append-only. Session write-outs stay temporary: they drain into these two homes and die. Reason: the composition layer works, but its editorial layer had not been kept current — the reasoning lived in uncommitted write-outs and session memories.

### Area of influence restored, as influence.md

Every mission declares its area of influence — the surfaces and files it expects to touch — a claim, not a final list. Not in the intent (the conversation often cannot know repo surfaces); the scribe declares it, the executor refines it as the work concretes. Its own artefact, `influence.md`, because the mission is a container: the planner's scheduler reads every live area for collisions without loading the missions, and the executor updates it without churning a dispatched `mission.md`. Reason: the concept was adopted in practice (June 2026, born from the AppLayout/core-di-lite merge collisions) but lived only in mission instances, never in the material — so the redesign lost it without deciding to. The scheduler's "touch-set" is rewritten to the SC's word.

## 2026-07-06

### Scout and Investigator are distinguished by the kind of question, not by output routing

Scout is codebase discovery: you want to discover the codebase. Investigator is detective work: you have questions you want answered. The old "feeds you / feeds the next phase / separate mission" framing is dropped wherever the live material carried it — the routing was plumbing, never the identity, and it misled a handler into treating Investigator-vs-Apostle as a one-mission-or-two fork. Deprecated skills keep the old text: old skills are left as they are, not maintained.

### The Postmaster is a new operator role — the release phase is not a second Courier

Publishing was split out of the Courier. The Courier delivers the work into review (the PR, git ground); the Postmaster makes the merged work public (tags, releases, publish workflows, the registry — no working-tree changes). One word carrying both jobs is how a release phase wobbled between Maker and Courier across the June releases. The name: the mailroom analogy is kept deliberately — a semi-opaque name funds only the true half-guess ("sends the work out") and leaves the dangerous specifics to the role text, and when Claude guesses anyway the guess is visible instead of camouflaged as plausible trained behaviour. Plain "Publisher" was considered and passed over for exactly that camouflage risk.

### The identity frontmatter drives; skills.mjs parses it

`shared/pane/skills.mjs` now reads each actor's and role's `skills:` (and the handler's `roles:`) from the `ACTOR.md`/`ROLE.md` frontmatter, via the `yaml` dependency — the hand-kept mirror is gone, and each identity file is the single source for what it loads. The handler launch scripts share one role list (`HANDLER_ROLES`), and `launch-handler` no longer accepts a `skills` input from the Planner — a launch cannot carry a skill list that drifts from the material. Only the foundational set stays hard-coded, mirroring `~/.claude/CLAUDE.md`'s `Load:` lines, which have no frontmatter to read. Role order settled: `… scribe, executor, router`.

### The Apostle is a Maker who doesn't write code — rewritten off the designer framing

The role was rewritten around the SC's frame: same job and discipline as the Maker, but the change lands in a plan file in one write after many reads — that cheapness, plus the SC catching bad code before it lands, is the whole value. Design was never the role's: if the SC wanted design he'd cast an Engineer. Two rules made explicit: (1) the only permitted deferral to the Maker is code that needs the compiler's feedback to get right (difficult/complex types and generics) — "hard" is not an exit, and every deferral is declared in the plan; (2) on a re-prompt, approved iterations join the upstream decisions — the re-prompt names what may change and everything else is frozen. Reason: an Apostle re-prompted for rigour redesigned settled work (killed `toolInputKeyedBy`); the old role bounded only the first pass and its "Code as standard" section funded the designer self-image.

### Apostle refinement: review-earlier, and iterations are the review cycle

Two refinements to the rewrite above, same day. The first value is not a quality gate ("catch bad code") but timing: the SC reviews the code and makes changes earlier rather than later, when a change costs one re-prompt. And iterations — which are common — are the review cycle: a re-prompt is a review comment, answered like code review; unasked rework makes accepted parts unreviewed again and forces a re-read, destroying the cheapness the role exists for.

### Role skills ride the identity — the dispatch path loads them, not the handler

`launchCli` now unions `roleSkills(role)` (from `roles/<role>/ROLE.md`) alongside the `actorSkills(actor)` it already added, so a dispatched cast gets its role's craft skills automatically — a Maker arrives with `tdd`, `tech-debt`, `typescript-standards`, `technical-writing`, `sc-commit-writing`, `sc-ghostwriting` whether or not the handler lists them. The handler's `skills` array becomes purely additive: foundational plus any per-phase extras the mission's `## SKILLS` section names beyond the role's own set. Reason: a Maker was dispatched with none of its craft — the mission's `## SKILLS` section was the only source, which left it to the handler, who missed it. Role skills are identity, not a hand-assembled list; the same way actor skills already rode the identity, role skills now do too. The declarations already lived in the ROLE.md frontmatter — only the loader was not reading them.

### Mode markers become emojis; a switch shows both ends

Mode state is now declared with an emoji rather than words: `💭` conversation, `⚡` execution (the plan rides on the execution marker: `⚡ [plan]. Not: [exclusions]`). Staying in a mode is the bare glyph; a switch names both ends as a pair, `from→to` (`💭→⚡`, `⚡→💭`), so the transition reads itself and the enter/continue distinction survives. The first turn of a session is the bare glyph for the mode it opens in, since there is no prior mode to pair with. Reason: an emoji is faster to scan than two words and primes generation the same way the teapot marker does; the from→to pair keeps the transition legible without a wordy label. Framing: the teapot markers are the envelope around the whole response (opening and closing), and the mode marker sits inside it. That ordering is spelled out as a small section in both teapot-protocol and claude-philosophy, each from its own side.

### The skills repo refers to nothing in the fleet repo

The material must be self-contained: a skill or identity file pointing casts at fleet-repo scripts or references is a broken reference, not an instruction. Settled while auditing the worktrees skill — it named `fleet/scripts/dispatch-worktree.mjs`, and the question "should they be using that script?" answered itself. Landed in one sweep: `dispatch-worktree.mjs` migrated into the worktrees skill (its two copy functions folded into one — files intentionally gitignored and needed get carried, because a worktree clones the repo, not the directory); `rebase-worktrees.mjs` migrated into mission-integration (now resolving its target fleet from the run directory, since its own path no longer says which fleet); `starter-CLAUDE.md` into project-memory's templates; prompt-template's dead `references/prompt-authoring.md` pointers repointed at the skill; the handler and executor rewordings so the fleet *data* repo's root `CLAUDE.md` (conventions + open items — a legitimate data home, verified live) is not mistaken for material. The fleet copies get deleted as each migration lands. Still pointing outward deliberately: `new-project-setup`, until it is built as a skill.

## 2026-07-08

### The verification commit: verification done = commit, everything

When mission verification passes, the executor commits **everything** in the handler repo, immediately — the verification commit. It is a checkpoint, not a changes-commit: it pins the state the mission was verified in, so later changes diff against the verified baseline. Not gated on the SC's review or anything else — verification done = commit, end of story. Reason: handlers kept objecting ("only my changes should be committed") by applying the shared-repo staging discipline where it does not belong; the material now carries the reasoning so it stops being re-derived. In `mission-verification` and the handler ACTOR.

### The scribe never writes a role's stance; only the SC countermands a role

Four rules, landed together after a scribe pasted Investigator language ("you map the problem; you do not design the solution") into an Apostle phase without ever opening `apostle.md` — the cast obeyed it and produced a plan with none of the code, costing the SC hours. (1) The scribe never writes role-stance prose — the block owns the stance; the scribe fills mission-level content into its slots (`prompt-authoring` > The blocks own the stance). (2) Provenance's Fleet source explicitly includes the role's `ROLE.md` and phase block — a stance sentence traces there or to the SC, or it is invented (`mission-grounding`). (3) The scribe must actually open the block and `ROLE.md` of every role in the squad before composing — a listing is not a read. (4) Verification fails any instruction that runs counter to the phase's role unless it traces to the SC's words in `intent.md` — an override of a role can only come from the SC (`mission-verification`, check one).

### Cast-launch configs are zod schemas; `skills` is mandatory; the supervisor mirrors the operator's role

The three cast-launch scripts (`new-operator-cast`, `new-supervisor-cast`, `next-phase-cast`) now validate their stdin config against zod schemas (`skills/dispatch/scripts/config.mjs`, zod added as a dev dependency): a missing mandatory field or an unknown key exits 2 before anything launches. `skills` is mandatory on every dispatch — an empty array is a valid value, an absent field is a broken dispatch. Reason: the hand-rolled required-field loops never checked `skills`, and the SKILL.md config listings never documented it (a known open item, flagged in a post-mortem and left unfixed), so a supervisor launched with no foundational skills at all. `new-supervisor-cast` also requires `operatorRole` — the role the operator was dispatched with — passed through so the supervisor's cast unions the same role skills the operator got, because the supervisor judges skill application and must hold the same set it judges by.

### The supervisor is the repository's gatekeeper; the verdict starts at BLOCK

The supervisor ACTOR.md now states the posture directly: the supervisor is not judging the work, it is defending the repository from garbage. The verdict starts at BLOCK and only verified quality raises it to PASS — you do not sit an exam and pass by walking out; you start at zero and every mark is earned. An item not actually verified (a skill marked without its `SUCCESS.md` read, a diff judged unread) raises nothing. Reading a skill's `SUCCESS.md` is a precondition of marking it. Reason: the token-stats supervisor passed two iterations on fabricated skill marks — "expected/actual naming — present" written without opening the skill or the assertions — and defended the PASS turn after turn, because its posture was "is the work that bad?" pulling a default pass down instead of quality raising a default block up.

### Model choice is right-sizing; Sonnet is the default, the supervisor is a safety net

With sonnet-5 available the model roster is sonnet-5 / opus-4-8 / fable-5 — a capability ladder. Sonnet is the default for operators and supervisors; Opus for medium-difficulty work (coding, investigating, the Apostle); Fable only in extremely complex circumstances — most of what we do won't need it. Where stakes drive the pick, the choice is laid out for the SC (a code review picks Opus or Fable depending on how critical finding bugs is). Reason: throwing more resources at a problem does not make it more efficient — the pick is right-sizing capability to the work. The supervisor runs Sonnet because it is better to invest in the one doing the work than the one catching it: the supervisor is a safety net, not the tightrope. The defaults table lives in `squad-selection`, with the matching note in its PHILOSOPHY.

### The scribe is a role the handler takes; the structural separation is writer/verifier

Supersedes part of "The scribe is a separate session" (above, same date): what is structural is that the session that writes the mission never verifies it — not that the writer is a session apart from the one that drew the intent. Understanding what the SC wants is the precondition for writing, and the session that drew the intent already holds it; a cold writer reconstructing understanding from files is where the drift enters. `scribe` returns to the handler's `roles:` frontmatter. Reason: the stage2-speak scribe (claude-cli) delivered neither understanding nor independence — it drained a richly-described goal into a checklist, paraphrased away the behavioural requirement, never opened the governing blueprint, invented a surface-plausible test, and its provenance pass verified its own draft against itself.

### The scribe writes from understanding, carries the SC's words intact, and the mission stands alone

Four sections added to the scribe ROLE.md, from the same incident. (1) Understanding before writing: read every file in the mission directory and every document a source names as governing; answer what-for / why / what-done-looks-like / how-anyone-would-know before writing a line. (2) Carry the words: goal, vision, and settled decisions land in the intent's own words — add nothing, take nothing away; paraphrase is where requirements drop. (3) The mission stands alone: the front artefacts exist to create it and could be discarded after; no filename references to `intent.md`/`squad.md`/`influence.md` (`blueprint.md` stays the referenced exception) — also stated in `mission-artefacts` at the equation. (4) The goal lives in the mission: it opens the mission and every phase serves it; a behavioural goal names where it is demonstrated.

### Grounding: governing documents join the sources; the upward trace checks intact and covers goal and objectives

Three changes to `mission-grounding` (SKILL + TEMPLATE). A document a source names as governing becomes mandatory reading and a source in its own right — a claim grounded in a summary of it is ungrounded (the scribe never opened the blueprint the intent said governs, and invented a near-match of its real requirement). Carried means carried intact, in the intent's words — a paraphrase that lost the requirement is `DROPPED`, not carried. And the upward trace gains a Coverage table: the goal and each objective trace to the phase that does them (`Done by`) and the place they are proven (`Proven at`); `UNCOVERED` goes back upstream to the SC — stage2-speak carried an objective assigned to no phase and a behavioural goal no phase demonstrated, under a fully passing downward trace.

### Dispatch is three scripts; the default is a fresh cast, and there is no recast supervisor

The five cast/recast scripts (`new-operator-cast`, `new-supervisor-cast`, `next-phase-cast`, `recast-operator`, `recast-supervisor`) are replaced by three: `scaffold-panes` (panes only, once, at mission start), `cast-operator`, and `cast-supervisor`. Both cast scripts require `phase` and `iteration`. The process, stated in the SKILL and enforced by the zod schemas: every dispatch is a fresh cast by default. The operator at iteration >1 must carry `template` (`revise` | `mission-updated`) and `resume` (boolean) — `resume: true` is the one recast that exists, because the operator's in-flight context is sometimes the point; at iteration 1 both fields are forbidden. The supervisor is always a fresh cast: its schema has no `template` or `resume`, so a recast supervisor is unrepresentable, and its envelope tells the cast it is only ever a cast. Reason: a handler recast a supervisor — the old skill documented a menu, not a process, and `recast-supervisor verify` was the only path with "supervisor" in its name, so handlers reached for it; a supervisor that re-judges with its own last verdict in context defeats the fresh-eyes point. The wrong dispatch is now unexpressible rather than merely discouraged.

### provenance.md is the scribe's proof, and verification refuses to run without it

Two sides of one fix. `mission-verification` gains a hard precondition: no `provenance.md` beside `mission.md`, no verification — the verifier does not improvise a trace or run check two alone; the mission goes back to the scribe as unfinished. The scribe material (ROLE.md, `mission-grounding`) states the ownership: `provenance.md` is the scribe's proof, produced as part of writing — the deliverable is `mission.md` *with* its proof, and the scribe never verifies its own mission; verification is a different cast's pass run against the proof. Reason: verifications kept running on missions with no provenance, and handlers acting as scribe wrote `mission.md` then treated `provenance.md` as a separate verification task rather than their proof — the pass either verified nothing or the wrong cast did the grounding.

### The mission skills reinforce each other; the scribe role names its two postures and their pairs

Composable does not mean isolated. `prompt-authoring` — the one skill both sides of a mission load — now names its pairings from its own side: writing = `prompt-authoring` + `mission-grounding` (the proof), verifying = `prompt-authoring` + `mission-verification` (the cross-check), with an instruction to stop and load the missing half before any work. The scribe ROLE.md states the two postures — write or verify, never both for one mission — each entered by loading its pair, and `mission-verification` joins the scribe's frontmatter `skills:` so the verify posture is loadable from the role. Reason: a handler adopted the scribe role in-session, ran on the role's summary prose plus `create-mission` alone, and produced a "done" mission with no grounding — the requirement existed only as dispatch-time injection and prose it never opened; nothing in the skills it did open pointed at the half it was missing.

### A role's SAM block may be keyed by posture; the scribe verifies as `brings`

The scribe holds two postures — write and verify, never both in the same session — and they sit at different SAM positions, so the frontmatter `sam:` block now keys by posture: writer (carried, decided, tool), verifier (brings, decided, tool). "One point" survives as one point *per posture*. The role stays one role, not two: the scriptorium precedent — the corrector was a scribe, senior, reading a brother's copy against the exemplar; the craft is one, and what separates writer from checker is the person — the session — never the profession. This is not the many-hats problem that keeps roles apart: one role, a clean internal distinction, separated per session. The substance ruling came from substance's purpose, not its definition: substance is the licence axis — it tells a cast which direction it fails in. `carried` means adding is the sin (the writer's invention); `brings` means failing to add is (the verifier nodding a self-assessment through). The verifier's defining failure is the carrying failure, so its substance is `brings`. Follow-up owed: the glossary's SAM entry and the repo guide both describe a single-point `sam:` block and now have a counterexample on disk.

### Provenance is written first; the mission is composed from it; the author judges nothing

`mission-grounding` rewritten around the inversion. The scribe extracts the evidence from the sources into `provenance.md` — Evidence rows with an enum Source (`SC | Project | Fleet`, no other value) and the Text the scribe must actually produce — then composes `mission.md` from the rows and nothing else. `Carried` is filled as rows land (intact, in the intent's words); Coverage traces goal and objectives to done-by/proven-at; anything the mission needs that no source supplies is a Gap sent upstream, never filled. No verdict column exists anywhere: the fleet survey of all fifteen provenance files found every claim in every file marked `keep` — a self-verdict with a 100% pass rate, including on the one mission known to be wrong — and a post-hoc trace anchors the verifier on the author's account instead of the intent. Reason for the direction: written after, provenance justifies anything; written first, the sources are in front of the scribe at the moment the words form — the only moment grounding can happen. Honest limit, ruled by the SC: nothing enforces generation order — the skill primes the thinking, it does not gate it, and that priming is the only value the skill can provide. Lineage that forced the rewrite (traced through git): the procedure was copied from `devops-review` (third-party review, verdict native) onto self-review; the artefact format was extruded from the skill's own what-not-to-do teaching table (#303), whose failure rows are unreachable in a finished file; "Codebase" as a source was inherited from that example's investigation context and was always incoherent for a scribe. Full account in `mission-grounding/PHILOSOPHY.md`.

## 2026-07-09

### The investigation is a vehicle, not a source — referenced like the blueprint, never transcribed

`investigation.md` joins `blueprint.md` as the mission's second vehicle: an artefact with its own author, shipped in the mission directory, referenced by the mission and read directly by the operator — findings never transcribed into mission prose. Reason: the Investigator's findings are verified against code the scribe never reads, so the scribe cannot attest them as Evidence text — extracting them into provenance rows would put an operator's word in the proof wearing the SC's standing, and a transcribed finding masquerades as a decided instruction when it is a starting point the operator confirms on contact (findings-not-rules). Decisions the SC made *about* the investigation ("the fix follows it", "option two") are intent content and land in the mission as carried rows; the three-source enum stays three. This does not touch the standalone rule: the intent's content is still carried whole into the mission — `intent.md`/`squad.md` remain discardable; the vehicles are not discarded inputs but part of what ships. Landed in `mission-grounding` (SKILL + TEMPLATE row), `mission-artefacts` (investigation.md defined beside blueprint.md; the equation names two vehicle exceptions), `prompt-authoring` (the Context section stops saying "bake findings in"), and `mission-verification` (missing reference is a fail; transcribed findings are a fail).

### The gate is not scope — coding roles own every failing check they find

Added to the maker, builder, and cleaner ROLE.md files. The mission's scope says what to *change*; the Verify gate says what must *hold* — build, type-check, tests, everywhere. Different axes: the first never cancels the second. A failing check the operator finds is theirs, whichever package holds it — fix it, or stop and flag it loudly as blocking; never step around it and file it as "pre-existing, not mine." Reason: an operator found a real type error breaking `type-check --force`, wrote a memory warning the next session about it, and still ruled it "another package's problem, out of scope" — because every instruction with teeth points at the diff ("fix exactly F1–F5 and nothing else", stage only your files, scope-creep fails supervision) and nothing stated the opposite pole, so the defensible move was to protect the ticket boundary instead of the thing everyone depends on. The SC's test: the flatmate who tip-toes through the kitchen mess to make their cup of tea and tip-toes back is not careful — they are miserable to live with. Leave the kitchen better than you found it.

### The supervisor's iteration is a fixed template; the mission goal is its own section, answered on its own line

The supervisor ACTOR.md now shows the iteration as a fixed template at every stage, empty and completed, not prose rules: Plan (numbered boxes), Working (a separate section, deliberately — it harnesses the supervisor's generation drive as evidence, one numbered entry per plan item), Verdict, and a Goal served line. Marks are written into the Plan's own boxes: ✅ ❌ ❓ ➖ ⚠️ — ➖ is positive knowledge the item does not apply; "couldn't tell" is ❓. Every box carries a mark before the verdict. The mission goal gets its own section, first in the file: the mission's stated goal is the single most important part of anything, and the standing failure is that no one stops to read it — a supervisor passed a build where `/new` left the CLI unaddressable, the goal failing, filed as an observation under a PASS. "Does this serve the mission?" is the underlying question to everything; it is answered explicitly on the Goal served line, in addition to the verdict — the two are separate, and neither overrides or replaces the other. History: the role was previously stripped back because supervisors passed in their own judgment; this is the carpet laid back down as fixed structure, not restored free judgment.

### Skills declare diagrams in frontmatter; the d2 is the single source of truth

A skill that rests on a diagram declares it: `diagrams: [lifecycle]`, bare names. `buildSkillsBlock` (`shared/pane/envelope.mjs`) resolves each name from `~/.claude/diagrams` (a symlink to `docs/diagrams`) and nests a `<diagram name format="d2">` block inside the `<skill>` block, so the same d2 file is rendered for the SC and read by casts — one source, no prose copy to drift. A skill declaring a diagram that does not resolve fails to compose (exit 2). A generic `references:` key was rejected: it smuggles the type back in; `diagrams:` holds until a second artefact kind actually exists.

### The mission process splits into mission-preparation and mission-execution; roles are disposition, skills are process

Roles tell Claude who to be; process lives in composable skills. `mission-preparation` covers lifecycle stage 1, the SC's direction to ready — sequencing intent, squad, mission, and verification by their owning skills — loaded by the interlocutor, squad-selector, and scribe. `mission-execution` covers stages 2–4, dispatched to retired: the phase loop, cleanup, the seam to the post-mortem at completed·PR-merged (the lifecycle diagram is the authority for seams, not pane-close), and the post-mortem's wrapping of the mission — loaded by the executor, which shed its process sections. Each process skill states which stages it covers, so gaps and overlaps between them are visible. `dispatch` shrinks to a pure tool layer (the router's); its loop has no mission-end step. `close-mission.mjs` and `set-handler-status.mjs` (renamed from `set-pm-status`; the state `pm-running` renamed `handler-running` — pm was a project-manager holdover) live in `mission-execution/scripts`. Left open: whether dispatch is eventually swallowed by mission-execution when first-class tools replace the tmux panes.

### Effort is token budget, not capability; every phase names it, with defaults per role

Effort is approximately how much token budget the cast thinks it has: low finishes tasks earlier, higher spends more time and tokens — it is not capability. For one-shot operators the question is simply how much time and effort we want spent: fixed work gets low, producing a document gets more. Benchmarked (SWE-bench Verified, Opus): past high the resolve rate stops moving — 79% at high, xhigh, and max alike, at $0.66, $1.64, and $3.95 per solve — and on easy work low matches medium at half the cost. `effort:` is now required on every phase in `squad.md` (squad-selection TEMPLATE), with the defaults table in the SKILL's Effort defaults section, after Model defaults: the build and mechanical roles low (the Maker medium in a mission without an Apostle — it is doing the discovery too); Investigator, Apostle, and Architect high; Scout, Engineer, Reviewer, and Writer medium; the Supervisor low — it works a bounded plan, finish the checklist and stop. Selector layer only for now: the mission scripts and dispatch schemas still treat effort as optional, deliberately.

### The Cleaner's success is code quality; refactoring is its mechanism, taught by a skill

The Cleaner's success function is replaced, not extended: the win is the code meeting the bar — lint clean as the floor, structure above it — because quality never happens unless it is a phase's deliverable. The evening's evidence: no operator itches to improve anything; the trained win is task completion, and "out of scope, not mine" is always the winning move unless a phase's task *is* the quality. A new `refactoring` skill carries the how, because "refactor" alone licenses either redesign or nothing: green tree precondition, one small transformation at a time with the suite green after every step, behaviour constant (tests unchanged — an edit to a test means behaviour changed; stop), the bar anchored to the decided standards (`typescript-standards`, `tech-debt`) and never extended by taste, redesign and behaviour changes flagged up, each refactor recorded in the debrief. The Cleaner runs at the safest moment for structural change — tree green, behaviour pinned by the suite — and its licence resolves `typescript-standards`' "leave pre-existing code alone unless asked": for the Cleaner, cleaning is the asking. SAM block added: brings (the improvement is its contribution; its failure is failing to bring — linter-passes-done), material (its truth is the code and the green suite), tool (the diff).

## 2026-07-10

### The communication model: foundation + voice + audience + medium

Every act of communication composes as foundation + voice + audience(s) + medium, and every rule lives at the most general layer where it holds unqualified — strip the medium, the audience, the voice; where the rule breaks is its layer. Voice is whose name the output goes out under (Stephen or Claude — the sc- prefix was convention, not the model). Audience is the role types reading it, a set per artefact: a work item is read by developers, product owners, stakeholders, the SC, and Claude at once. Medium is the form. Stephen the person and the SC are two audiences — the person is global and shareable; the SC is a system role that extends it (commander-protocol plus digest-never-relay and the phase report). Built as seventeen skills named by layer (`communication-fundamentals`, `voice-*`, `audience-*`, `medium-*`), refactored in two steps — a pure move verified by a separate review for anything added or lost, then the new content on the clean baseline — with the reasoning in `skills/PHILOSOPHY.md`. Reason: the general principles were trapped in format skills (the SC kept having to point sessions at `sc-doc-writing`), and re-encoded per medium; the model gives each rule one home and makes placement testable.

### Skills declare dependencies in frontmatter; composition happens at launch

A skill names what it rests on in a `skills:` frontmatter key, dependencies pointing down the model's layers only. The loader (`shared/pane/skills.mjs` `withDependencies`, applied in `skillsFor` and `buildSkillsBlock`) expands the closure at composition time, so naming `medium-commit` delivers `audience-developer` and `communication-fundamentals` with it, and role frontmatter lists shrink to what the role itself adds. The rendering is generated, never hand-kept: `scripts/skill-dependencies.mjs` writes `docs/skill-dependencies.md` from the frontmatter and fails on an upward edge or a missing dependency. `scripts/start-claude.mjs` launches a plain session with the foundational set injected via `--claudeMd`, and the global `CLAUDE.md` was cut to the three pieces that are operating content (the missing-skill failure rule, Writing to files, Protocol stays on) — the `Load:` lines and per-skill blurbs existed only for hand-loading, which injection replaces. The foundational array swapped `clear-communication` and `executive-communication` for `communication-fundamentals`, `voice-claude`, `audience-stephen`, `audience-sc`; the identity frontmatters swapped to the new names; the nine superseded skills are marked deprecated in place, old text kept.

### The loaders resolve from their own checkout, not through ~/.claude

`skills.mjs` and `envelope.mjs` read `actors/`, `roles/`, `skills/`, and `docs/diagrams/` relative to the module's own location instead of `~/.claude`, whose symlinks always point at the main checkout. Reason: code in the repo reaching out to a global that points back at a different copy of the same repo was self-inconsistent — a worktree's loaders composed main's material, so a branch could never test its own identity changes. Now every checkout composes from its own tree. The `~/.claude` symlink farm remains for sessions that load skills by hand; composition no longer goes through it.

## 2026-07-11

### A skill not worth marking gets no SUCCESS.md; absence is the statement

The original rule — a SUCCESS.md for every skill, some saying "not marked" — was written when there were six skills. Past a hundred, SUCCESS files are loaded surfaces: a file whose whole content is "look elsewhere" pays tokens on every load to say nothing. So a skill not worth marking gets no file at all, and absence means not marked. The existing not-marked files predate the change and stand until removed; no new ones are added. Reason: the SC — "consider that all these success files get loaded; if a file is not needed, don't add it" — the every-skill rule predates the scale.
